1. FLUJO FUNCIONAL OBLIGATORIO
==================================================

El flujo debe funcionar exactamente así:

1. Un usuario interno autorizado, como agente, vendedor, comercial, director o gerente, crea una cotización desde la vista actual de cotizaciones.

2. La cotización se relaciona con:
   - businesses
   - branches
   - representatives
   - quotations
   - quote_products
   - el usuario interno que creó la cotización mediante quotations.user_id

3. El correo del representante es obligatorio. Si no hay correo válido:
   - no permitir finalizar la cotización;
   - mostrar un error claro;
   - no intentar crear una cuenta sin correo.

4. Después de guardar correctamente la cotización y sus productos, se debe ejecutar una Supabase Edge Function que:
   - reciba quotationId;
   - valide el JWT del usuario interno;
   - confirme que el usuario tiene permiso para crear/enviar cotizaciones;
   - consulte la cotización, el representante, la empresa y el correo desde la base de datos;
   - no confíe en nombres, roles, representativeId, userId ni correo enviados libremente desde React.

5. Si el representante todavía no tiene cuenta:
   - crear/invitar el usuario mediante supabase.auth.admin.inviteUserByEmail();
   - usar como redirectTo:
     `${APP_URL}/establecer-contrasena`
   - utilizar el email almacenado en representatives.email;
   - guardar metadata útil como:
     representative_id,
     business_id,
     role_code: "cliente",
     application_code: "ecommerce";
   - establecer app_metadata.must_change_password = true;
   - no sobrescribir metadata existente: combinarla;
   - obtener el UUID real de auth.users;
   - actualizar representatives.user_id con ese UUID;
   - crear o actualizar profiles;
   - asignar el rol cliente en user_memberships;
   - asignar acceso a la aplicación ecommerce en user_applications;
   - buscar los IDs reales de roles y applications por role_code/application_code, no escribir UUID fijos;
   - mantener todos estos procesos idempotentes mediante upsert o consultas previas;
   - nunca crear dos cuentas para el mismo correo.

6. Si el representante ya tiene cuenta pero todavía no activó su acceso:
   - no crear otra cuenta;
   - volver a enviar un enlace de activación o recuperación dirigido a `/establecer-contrasena`;
   - mantener must_change_password = true;
   - vincular representatives.user_id si todavía está vacío.

7. Si el representante ya tiene cuenta activa:
   - no volver a invitarlo;
   - no obligarlo a cambiar nuevamente su contraseña;
   - enviar un correo normal indicando que tiene una nueva cotización;
   - incluir número de cotización, empresa y botón “Ver mis cotizaciones”;
   - el botón debe llevar al login principal o al portal del cliente;
   - usar el mecanismo de envío de correos existente en el proyecto;
   - si no existe un mecanismo para correos normales, crear una Edge Function reutilizable usando secretos de entorno:
     SMTP_HOST
     SMTP_PORT
     SMTP_USER
     SMTP_PASS
     SMTP_FROM_EMAIL
     SMTP_FROM_NAME
     APP_URL
   - no escribir credenciales SMTP en el repositorio.

La invitación es solamente para la creación/activación inicial de la cuenta. Las siguientes cotizaciones producen una notificación, no una cuenta nueva.

3. EDGE FUNCTION invite-quotation-representative
==================================================

Crear:

supabase/functions/invite-quotation-representative/index.ts

Requisitos:

- Responder correctamente a CORS y OPTIONS.
- Requerir Authorization Bearer.
- Validar al usuario llamante mediante su JWT.
- Utilizar un cliente normal para identificar al usuario.
- Utilizar un segundo cliente administrativo con SUPABASE_SERVICE_ROLE_KEY solamente dentro de la Edge Function.
- No devolver secretos, tokens ni datos sensibles.
- Normalizar el correo con trim().toLowerCase().
- Consultar quotationId en quotations.
- Consultar representatives mediante quotation.representative_id.
- Verificar que el representante esté activo.
- Confirmar que representatives.email exista.
- Verificar que el usuario llamante sea:
  a) el creador de la cotización, o
  b) posea un rol/permisos existentes que permitan administrar cotizaciones.
- Adaptar la comprobación al modelo actual de profiles, user_memberships, roles y permisos.
- No permitir que un cliente invoque esta función para otras cotizaciones.

Para detectar una cuenta existente:
1. consultar profiles por correo normalizado;
2. usar profiles.user_id cuando exista;
3. si es necesario, comprobar Auth Admin desde el servidor;
4. no usar Auth Admin desde React.

Para una cuenta nueva:

const { data, error } =
  await supabaseAdmin.auth.admin.inviteUserByEmail(email, {
    redirectTo: `${APP_URL}/establecer-contrasena`,
    data: {
      representative_id: representative.representative_id,
      business_id: representative.business_id,
      full_name: representative.name,
      role_code: "cliente",
      application_code: "ecommerce"
    }
  });

Después:
- obtener data.user.id;
- leer y combinar app_metadata existente;
- establecer must_change_password: true;
- establecer role_code: "cliente";
- establecer application_code: "ecommerce";
- actualizar el usuario con auth.admin.updateUserById();
- vincular las tablas empresariales.

No sobrescribir perfiles o membresías existentes innecesariamente.

El proceso debe soportar múltiples cotizaciones para el mismo representante sin duplicar:
- auth.users;
- profiles;
- representatives;
- user_memberships;
- user_applications.
