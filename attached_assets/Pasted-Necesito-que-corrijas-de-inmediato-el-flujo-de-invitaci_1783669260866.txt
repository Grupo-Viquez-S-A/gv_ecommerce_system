Necesito que corrijas de inmediato el flujo de invitación y establecimiento obligatorio de contraseña de los representantes.

Ya identifiqué que la Edge Function existente se llama:

create-representative-user

No crees otra función que duplique su responsabilidad. Modifica la función existente y conserva su lógica actual para:

- Crear o encontrar el usuario en auth.users.
- Crear o actualizar profiles.
- Enlazar representatives.user_id.
- Crear user_memberships.
- Crear user_applications.
- Evitar cuentas duplicadas.

El problema actual es que la función envía la invitación en algunos casos, pero no establece must_change_password, omite el correo cuando el usuario ya existe y puede enviar un redirectTo incorrecto o undefined.

Debes implementar el flujo completo de extremo a extremo. No quiero solamente una explicación. Modifica el código, crea la Edge Function adicional necesaria, actualiza el frontend y ejecuta npm run build.

==================================================
RESULTADO OBLIGATORIO
==================================================

El flujo debe funcionar exactamente así:

1. Un agente o usuario interno crea una cotización para un representante.
2. create-representative-user crea o vincula la cuenta del representante.
3. Si es una cuenta nueva, Supabase envía el correo usando la plantilla “Invite user”.
4. Al presionar “Aceptar invitación”, el representante debe ir exactamente a:

/restablecer-contrasena

5. El representante no puede entrar a ninguna ruta interna mientras no establezca su contraseña.
6. El representante escribe y confirma su nueva contraseña.
7. Se actualiza la contraseña.
8. Se marca must_change_password como false.
9. Se cierra la sesión temporal.
10. Se redirige al login principal.
11. El representante inicia sesión manualmente con su correo y nueva contraseña.
12. Se redirige a /mis-cotizaciones.
13. Puede ver únicamente sus propias cotizaciones.
14. Una segunda cotización no debe crear otra cuenta ni volver a forzar la contraseña.

- SITE_URL

APP_URL debe contener únicamente el origen de la aplicación, por ejemplo:

https://dominio-de-la-aplicacion.replit.app

Construye la URL así:

const appUrl = Deno.env.get("APP_URL");

if (!appUrl) {
  devolver un error 500 claro indicando que falta APP_URL;
}

const redirectTo = new URL(
  "/restablecer-contrasena",
  appUrl.endsWith("/") ? appUrl : `${appUrl}/`
).toString();

Antes de llamar a inviteUserByEmail, registrar en los logs de la Edge Function únicamente:

- redirectTo
- email normalizado

No registrar tokens, contraseñas, service role ni enlaces completos de autenticación.

No uses el dominio enviado desde el frontend.

3. USUARIO EXISTENTE
==================================================

Actualmente la función encuentra el usuario existente y continúa sin enviar ningún correo. Eso debe corregirse.

Cuando el usuario ya exista:

1. Obtener el usuario completo mediante:

supabaseAdmin.auth.admin.getUserById(userId)

2. Leer:

- app_metadata.must_change_password
- app_metadata.activation_status
- last_sign_in_at
- invited_at
- email_confirmed_at

3. Determinar su estado.

CASO A: usuario ya activo

Considerar activo cuando:

- app_metadata.must_change_password === false, o
- app_metadata.activation_status === "active", o
- tiene last_sign_in_at y no tiene una activación pendiente explícita.

En ese caso:

- No enviar otra invitación.
- No enviar recuperación de contraseña.
- No cambiar must_change_password a true.
- Mantener la vinculación con profiles, representatives, user_memberships y user_applications.
- Devolver:

{
  ok: true,
  account_state: "active",
  invitation_sent: false,
  must_change_password: false
}

CASO B: usuario existente con activación pendiente

Considerar pendiente cuando:

- app_metadata.must_change_password === true, o
- app_metadata.activation_status === "pending", o
- fue invitado, nunca inició sesión y todavía no terminó la activación.

En este caso:

- Mantener must_change_password en true.
- No intentar crear otra cuenta.
- Crear un cliente público separado con SUPABASE_URL y SUPABASE_ANON_KEY, sin reutilizar el Authorization del usuario interno.
- Enviar un correo de recuperación para que pueda establecer la contraseña:

await supabasePublic.auth.resetPasswordForEmail(email, {
  redirectTo
});

Este correo utilizará la plantilla “Reset password”.

Devolver:

{
  ok: true,
  account_state: "pending",
  invitation_sent: true,
  email_type: "recovery",
  must_change_password: true
}

No utilices una recuperación de contraseña para usuarios activos cuando solamente se crea una nueva cotización.

CASO C: usuario legado sin estado claro

No fuerces masivamente a todos los usuarios existentes.

Si falta la metadata y el usuario nunca inició sesión, puedes marcarlo como pendiente.

Si el usuario ya tiene last_sign_in_at, tratarlo como activo para evitar bloquear cuentas que ya funcionan.

==================================================
4. NO VOLVER A FORZAR LA CONTRASEÑA
==================================================

Una vez que un representante complete la activación:

- must_change_password debe quedar en false.
- activation_status debe quedar en active.
- activated_at debe guardar una fecha ISO.
- Las futuras llamadas a create-representative-user no deben cambiar estos valores a pending.
- Las futuras cotizaciones no deben volver a enviar la invitación.
- No debe volver a aparecer el formulario obligatorio de contraseña.

La bandera true solamente debe establecerse:

- al crear una cuenta nueva;
- al detectar una cuenta realmente pendiente que nunca terminó la activación.
